# Chat et analyse d'impact dans l'explorateur web — design (lot 2)

Date : 2026-10-13 · Suite du lot 1 (`2026-10-13-web-explorer-design.md`), déjà en ligne sur https://mge-agilos.github.io/dg-reform-tsi/

## Objectif

Ajouter à l'explorateur deux onglets, **Chat** et **Impact**. Ils réutilisent les services déjà validés en production sur la Haystack Enterprise Platform du client :
- `tsi-chat` : un Agent gpt-5.1 (EC GPT) avec les outils `search_projects`, `search_deliverables`, `search_csrs`, `list_projects` et `find_projects` ;
- `tsi-impact` : le même Agent avec `web_search` (SearchApi).

On ne crée pas de seconde implémentation du RAG : la page est une interface de plus devant les services du client.

## Architecture

```
Page (GitHub Pages, session testeur)
  │ POST {service, messages} + jeton de session Supabase
  ▼
Edge Function Supabase « haystack-proxy »
  1. vérifie le jeton (verify_jwt) puis rpc is_tester() avec ce jeton → sinon 403
  2. valide la requête (service connu, ≤ 20 messages, ≤ 8 000 caractères chacun, rôles user/assistant)
  3. POST <HAYSTACK_{CHAT|IMPACT}_URL> {model, messages, stream:false}
     Authorization: Bearer <HAYSTACK_API_KEY>      ← secrets de la fonction, jamais côté page
  4. renvoie {answer} (choices[0].message.content) ou une erreur lisible (sans secret)
  ▼
Gateway Haystack Enterprise (endpoint compatible OpenAI de chaque service)
```

- **Secrets de la fonction**, gérés dans le tableau de bord Supabase : `HAYSTACK_API_KEY` (clé API du workspace `tsi-reform`), `HAYSTACK_CHAT_URL` et `HAYSTACK_IMPACT_URL`. Ces deux URL sont les endpoints `/chat/completions` complets, copiés depuis la page de chaque service Gateway.
- **Variables optionnelles** : `HAYSTACK_CHAT_MODEL` et `HAYSTACK_IMPACT_MODEL`, qui donnent la valeur du champ `model` (par défaut : `tsi-chat` et `tsi-impact`). `ALLOWED_ORIGINS` (par défaut : l'URL Pages et `http://localhost:8000`).
- **CORS** : seules les origines autorisées passent, et la requête préalable `OPTIONS` est gérée.
- **Délai** : 140 s au maximum vers la plateforme, au-dessous de la limite des Edge Functions. Les services de la plateforme ont eux-mêmes une limite de 2 minutes par recherche.
- **Déploiement** : par l'interface Supabase (*Edge Functions > Deploy a new function > Via Editor*), en collant `supabase/functions/haystack-proxy/index.ts`. *Verify JWT* reste activé.

## Page

- **Onglet Chat**
  - La conversation est gardée dans la page (`sessionStorage`), avec un bouton « New conversation ».
  - Le champ de question est envoyé avec Entrée, et Maj+Entrée crée un saut de ligne.
  - Pendant l'attente, la page affiche « Thinking… (up to 2 minutes) ».
  - Les réponses en Markdown sont rendues avec `marked` puis assainies par `DOMPurify`. Les deux bibliothèques sont chargées depuis jsDelivr, en version figée. Les liens s'ouvrent dans un nouvel onglet.
  - Des questions d'exemple sont proposées, reprises de la recette de production.
- **Onglet Impact**
  - On choisit un projet par une recherche sur le titre dans la table `projects`, ou on arrive depuis la fiche d'un projet par le bouton « Analyse impact ».
  - La page envoie un seul message utilisateur : le titre du projet, son identifiant et ses pays.
  - Le rapport est affiché en Markdown, avec un bouton « Copy ». La dernière ligne du rapport donne le score d'impact.
- **Messages d'erreur**
  - 403 : « Access not authorised ».
  - 502 ou 504 : « The analysis service did not answer », avec la cause renvoyée par la fonction.
  - Délai dépassé : la page invite à réessayer.
- **Mentions** : « Answers generated by AI (gpt-5.1 via EC GPT): verify the cited sources. »

## Sécurité

- Le relais n'est accessible qu'à un testeur dont l'e-mail est confirmé (`is_tester`), parce que chaque appel consomme du LLM et de SearchApi.
- La clé Haystack ne quitte jamais Supabase.
- La fonction ne journalise ni le contenu des questions, ni les clés.
- La page n'insère du HTML qu'après passage par DOMPurify.

## Préalable côté plateforme (mise à jour du corpus)

Le corpus de production est encore celui de début octobre. Pour que le chat connaisse les CSR et les liens :
1. Exporter le corpus avec `prod-export`, déjà fait le 13/10 : 3 632 fichiers.
2. Supprimer les anciens fichiers `tsi-*` du workspace : 111 projets ont changé de nom avec la fusion du sitemap.
3. Téléverser le nouveau corpus par le SDK (`upload.ps1`), puis vérifier que l'index contient 3 632 fichiers et 99 981 morceaux.
4. Mettre à jour le pipeline `tsi-chat` avec le nouveau `pipeline-tsi-chat.yaml`, qui ajoute `search_csrs` et le filtre `csr`, puis le republier.

Le lot 2 fonctionne aussi avant cette mise à jour, mais le chat ignorera alors les CSR.

## Tests

- **Fonction**, sans dépendance réseau : la logique pure (validation, CORS, construction de la requête, extraction de la réponse) est isolée dans `supabase/functions/haystack-proxy/logic.ts`. Elle est testée avec `node --test` si Node est disponible, via un fichier `.mjs` qui importe la même logique en JavaScript, ou avec `deno test` si Deno est installé.
- **Page** : `node --check web/app.js`, et des tests manuels par l'utilisateur après déploiement. Le README contient une liste de contrôle.
- **Bout en bout** : un appel `curl` à la fonction avec un jeton de testeur, fait par l'utilisateur.
