# Production deployment on Haystack Enterprise Platform

Full corpus (projects, programme sheets, deliverables), **gpt-5.1 through the Commission's EC GPT gateway**
(`https://api.tech.ec.europa.eu/ecgpt/v1`, OpenAI-compatible API, key in the `GPT_EC` secret), published through
the Gateway. Validated beforehand on the trial (`deploy/trial/`): same chunking, same prompts, same pipeline
structures.

| File | Role |
|---|---|
| `index-tsi-corpus.yaml` | `tsi-corpus` index: one chunk per `#` section, hosted multilingual e5, OpenSearch |
| `pipeline-tsi-chat.yaml` | chatbot: gpt-5.1 Agent + `search_projects` + `search_deliverables` + `list_projects` + `find_projects` (files uploaded with the SDK, with their metadata) |
| `pipeline-tsi-chat-ui.yaml` | chatbot without `list_projects` or `find_projects`: use it when the files are uploaded through the web interface (only the metadata common to each batch) |
| `pipeline-tsi-impact.yaml` | impact analysis: gpt-5.1 Agent + `search_projects` + `search_deliverables` + `web_search` (SearchApi) |
| `pipeline-tsi-impact-openai-search.yaml` | alternative not used: OpenAI's built-in web search (too slow for the 2-minute limit) |
| `build_pipelines.py` | **generates** the three `pipeline-*.yaml` files (do not edit them by hand); the code of the `Code` components is in `src/tsi_agent/platform_code/` |
| `upload.ps1` | upload with the SDK, with checks; the key is read from the environment |
| `obsolete-files.ps1` | lists the workspace files that are no longer in the new release (to delete in *Files*) |
| `build/` (not in Git) | `files/` to upload and `manifest.json` (expected figures), generated by `prod-export` |

## Corpus

`python -m tsi_agent prod-export` writes one file per document: `tsi-project-<id>.md` (2,100),
`tsi-programme-<id>.md` (37), `tsi-deliverable-<id>.md` (498), i.e. **2,635 files and 83,900 chunks**
(6,212 project, 106 programme, 77,582 deliverable; largest file 3.3 MB). The exact figures of the current export
are in `build/manifest.json`.

- Each `# ...` section is one chunk of the local layer (250 words at most): a context title
  (project - programme year - country - section, or publication - document, p. N - programme year - country), the
  text, then the id, policy area, result, linked projects and source URL. The index splits at the `#` level only
  and finds exactly these chunks (checked locally on the 2,635 files).
- Each file has its `.meta.json`, which the platform copies onto its chunks: `Topic` (`TSI-BDG`), `corpus`
  (`dg-reform-tsi`), `doc_type` (`project`, `programme`, `deliverable`), `doc_id`, `title`, `countries` (ISO
  codes), `programme`, `year`, `policy_area`, `results`, `projects`, `multi_country`, `detail_page`, `source_url`,
  `chunks`. An unknown value is left out; each key has the same type in every file (checked at export).
- The search tools filter on `doc_type`: `search_projects` (projects and programme), `search_deliverables`
  (deliverables, cited with the document and the page), `search_csrs` (country-specific recommendations).
- CSRs (country-specific recommendations of the European Semester, 2016-2025, EU27): `tsi-csr-<ISO>-<year>-<n>.md`
  (903 files, ~2,700 chunks), `doc_type` `csr`, without `programme` or `policy_area` (different ECFIN taxonomy,
  in the text). Prepare them before the export: `python -m tsi_agent csr-fetch` then `csr-build`.
- Project -> CSR links (assessed by AI, `python -m tsi_agent csr-link`): the project's "Supported CSRs
  (AI-assessed)" section and the `csrs` metadata (ids of sub-parts, e.g. `csr-HR-2022-3.4`; the key is absent
  when there is no link). `list_projects` accepts `csr` (id or prefix, e.g. `csr-HR-2022`). Order before the
  export: `run` -> `deliverables` -> `csr-link` (never at the same time) -> `prod-export`.

## Aggregation questions (list_projects, find_projects)

A search returns only the 8 to 10 chunks closest to the question: for "how many projects" or "which countries",
the answer is spread over dozens of projects that the search does not see. As in the local version, the chatbot
has two tools that are not a similarity search:

- **`list_projects`** (exact counts on official criteria: country, policy area, programme, year, detail page,
  words of the title): `Code` (filters) -> `FilterRetriever` (**all** the project chunks matching the metadata,
  no top-k) -> `Code` (grouping by project, totals by programme, year, country, policy area, truncated list).
  The country filter is applied in the code: the result is exact whatever way the document store compares a list
  of countries.
- **`find_projects`** (free topic, e.g. money laundering): `Code` (filters) -> embedder -> the 400 closest
  project chunks and 300 closest deliverable chunks + the project catalogue -> `Code` (grouping by project: 60
  from the project texts, 30 from the deliverables, plus the projects whose title contains a keyword) ->
  **candidates that the agent assesses one by one** (rule 6 of the prompt), then counts computed by the agent on
  the projects it keeps.

The code of the `Code` components is in `src/tsi_agent/platform_code/` (tested: `tests/test_platform_code.py`)
and inserted as is into the YAML by `build_pipelines.py`. Checked locally end to end: the production YAML loaded
with an in-memory store instead of OpenSearch, and the `list_projects` totals equal to those of the catalogue.
Limit: a filtered OpenSearch query returns at most 10,000 documents; the corpus has ~6,200 project chunks (the
tool reports when the limit is exceeded). Prerequisite: the `Code` component and `FilterRetriever` are available
in the client's plan.

## Isolation within the client's organisation

The files of a workspace are not organised in folders, and **by default an index processes all the files of its
workspace**. The protections:

1. **Dedicated `tsi-reform` workspace**: files, index, pipelines, secrets and API keys of the project only.
2. **Index input router** (`input_topic_router`, `MetadataRouter`): only the files whose `Topic` metadata is
   **`TSI-BDG`** are indexed; the others go to the `unmatched` output, which is not connected (same convention as
   the client's other corpora, for example `RRP-CID`).
3. **Index file filter** (*Index > Settings*, to set before *Enable*): prefix `tsi-` **and** metadata
   `corpus == dg-reform-tsi`. A foreign file dropped into the workspace is not indexed.
4. If another index ever shares this workspace: give it the opposite filter `corpus != dg-reform-tsi`
   (only possible through the API, `PATCH /api/v1/workspaces/{workspace}/indexes/{index}`).

## To provide or check on the client side

- **Plan**: hosted `DeepsetNvidia*` embeddings (model `intfloat/multilingual-e5-base`) available; maximum
  duration of a search (2 minutes in the documentation: this is why the impact analysis is limited to 4 web
  searches); number of documents in the index (~84,000).
- **API URL** of the client's platform (region) and a **workspace API key** for the upload.
- **LLM**: the **`GPT_EC`** secret (EC GPT gateway key) in the workspace's *Settings > Workspace > Secrets*, with
  exactly the name of the variable read by the pipelines; the `gpt-5.1` model offered by the gateway, with tool
  calling. The platform's OpenAI connector is not used: the model is declared by the gateway's address. If the
  interface shows "Model (custom) is not connected", the pasted pipeline still declares the direct OpenAI model:
  paste the current generated version.
- **SearchApi integration** (*Settings > Integrations*, client's account, paid plan: the free trial is limited to
  100 searches; plans from $40/month for 10,000 searches; one impact analysis makes 4 at most). If the web search
  reports a missing key, also add a `SEARCHAPI_API_KEY` secret to the workspace.
- **Validation**: the configuration was validated on the trial with gpt-5.4; gpt-5.1 through EC GPT must be
  validated again with the acceptance tests (impact scores, citations, duration).

## Steps

For an update with a data release (download, upload, checks), follow [GUIDE.md](GUIDE.md); the steps below
describe the first installation.

### 1. Workspace and integrations

Create the `tsi-reform` workspace (*Settings > Organization > Workspaces*), add the `GPT_EC` secret (*Settings >
Workspace > Secrets*), connect SearchApi, and create an API key for this workspace (*Settings > Workspace > API
Keys*).

### 2. Generate and upload the corpus

```powershell
.venv\Scripts\python.exe -m tsi_agent prod-export        # exit code 1 if the metadata types are inconsistent
pip install haystack-enterprise-sdk                       # in a separate Python environment
$s = Read-Host -AsSecureString "Workspace API key"
$env:API_KEY = [Runtime.InteropServices.Marshal]::PtrToStringAuto([Runtime.InteropServices.Marshal]::SecureStringToBSTR($s))
$env:API_URL = "<client's API URL>"
$env:DEFAULT_WORKSPACE_NAME = "tsi-reform"
.\deploy\prod\upload.ps1
```

`upload.ps1` checks the manifest and the number of files, then runs `haystack-enterprise upload ...
--write-mode OVERWRITE`. The SDK attaches each `.meta.json` to its file (drag and drop in the interface does not:
the `.meta.json` files become ordinary files there). Check in *Files*: 2,635 files, and the metadata visible on
one of them.

### 3. Index

*Indexes > Create Index* -> YAML view -> paste `index-tsi-corpus.yaml` -> name **`tsi-corpus`** -> *Save*. Before
enabling it: the index's *Settings* -> *File Name Prefix Filter* `tsi-` and *File Meta Filter* `corpus` =
`dg-reform-tsi`. Then ⋯ -> **Enable**. Check once the status is *Indexed*: *Indexed files* = 2,635,
*Documents in index* = 83,900, *Failed files* = 0.

### 4. Pipelines

For `pipeline-tsi-chat.yaml` then `pipeline-tsi-impact.yaml`: *Pipeline Templates > Create empty pipeline* ->
YAML view -> paste -> name it `tsi-chat` / `tsi-impact` -> *Save*. Check the Haystack version in the pipeline
settings (3.2.0). Accept the updates suggested by the platform only after a first test, then copy the resulting
YAML back into this folder.

**Publish > Publish through Gateway > Publish to new service**: one service per pipeline (`tsi-chat`,
`tsi-impact`). The Gateway gives each one a stable address (including an OpenAI-compatible `/chat/completions`
endpoint), a publication history and the hosting settings: in production, set the minimum number of instances and
the idle timeout according to the expected usage (an idle instance costs nothing, but the first request is
slower).

### 5. Acceptance tests

In each service's Playground, start a new conversation for each test. For each one, note the duration and the
tokens (*Analytics*: traces). Some questions are in French on purpose (the chatbot must answer in the language of
the question); the English meaning is given in parentheses.

Chatbot (`tsi-chat`):
- « Quels projets ont soutenu la transformation numérique de l'administration grecque ? » (Which projects
  supported the digital transformation of the Greek administration?) then « Et en Croatie ? » (And in Croatia?):
  answer in French, citations [n], a "Sources" list, conversation history taken into account.
- « Le projet Barnahus en Slovénie a-t-il atteint ses objectifs ? » (Did the Barnahus project in Slovenia achieve
  its objectives?): "achieved", 2018 agreement, 2021 law, opening on 27 May 2022.
- "What did the deliverables of the Spanish primary care project recommend?": passages of deliverables cited with
  the document and the page (`search_deliverables` tool).
- "What CSRs did Croatia receive on public administration since 2022, and how were they assessed?":
  `search_csrs`, cites `csr-HR-2025-3` (Some Progress) and `csr-HR-2024-2` with their assessment (local run,
  13 October 2026).
- "Which projects support Croatia's 2022 country-specific recommendations?": `list_projects` with
  `csr=csr-HR-2022`, links presented as assessed by AI (local run: 2 projects, CSR 3.4 energy).

Aggregation (known exact answers, benchmark of 8 October 2026; check in *Analytics* which tool was called):
- « Quels pays ont des projets TSI ou SRSP dans le domaine « gestion des migrations » ? » (Which countries have
  TSI or SRSP projects in the "migration management" policy area?): 3 countries (`list_projects`).
- « Combien de projets dans le domaine « compétences, éducation et formation » pour le pays Grèce ? » (How many
  projects in the "skills, education and training" policy area for Greece?): 3.
- "How many projects does Latvia have in revenue administration and public financial management?": 5.
- « Quels pays ont des projets sur la lutte contre le blanchiment de capitaux ? » (Which countries have projects
  on the fight against money laundering?): 21 countries (`find_projects`, 28 relevant projects; local: 21/21).
- "Which countries have projects on wildfires or forest fires?": 8 countries.

Impact analysis (`tsi-impact`), with the project title as the query:
- "Barnahus Slovenia: Supporting children victims of violence": expected 7-8/10 (trial 7, local Opus 8).
- "Technical Support in transforming the existing fully state-administered funded pension scheme in
  Lithuania": expected ~2/10 (trial 2, local 2).
- Web sources as clickable Markdown links; last line "Impact score: X/10 … — Confidence: …".

## Web search

`web_search` queries SearchApi (Google engine, 5 results), reads the pages found and returns their URL and the
beginning of their text: this is the configuration validated on the trial (~30 s per analysis, scores consistent
with the local version). The analysis itself is done by the client's LLM (gpt-5.1 through EC GPT).

Alternative `pipeline-tsi-impact-openai-search.yaml`: OpenAI's built-in web search, through a sub-pipeline
(gpt-5.4 + the `web_search` tool of the Responses API; a Haystack Agent cannot mix this built-in tool with its
own tools). No SearchApi account is needed, but each search takes several tens of seconds: on the trial, the
analysis was cut off after 2 to 3 minutes (`CancelledError`), even in a lighter version (3 searches, reduced
context). Only consider it if the client's plan allows a longer duration or Jobs.

## Validation on the trial (9 October 2026)

`tsi-impact` configuration (gpt-5.4, SearchApi, scoring grid) tried on the trial with the projects index
(`deploy/trial/pipeline-tsi-impact-openai.yaml`):

| Project | Score | Reference (local Opus / trial Claude) |
|---|---|---|
| Barnahus Slovenia | 7/10 (strong) | 8/10 / 7/10 |
| Pension scheme Lithuania | 2/10 (weak), two runs | 2/10 / 2/10 |

Without the detailed grid, gpt-5.4 scored Lithuania 4/10 (deliverables counted as impact). Duration well below
the 2-minute limit. gpt-5.4 chatbot: correct, cited answers, but less complete lists than with Claude, hence
rule 6 (2 to 3 reworded searches); deliverables and `doc_type` filters to be validated at the client.

## Corpus updates

Run the extraction again (`run`, `deliverables`), then `prod-export` and `upload.ps1`: `OVERWRITE` replaces the
changed files and the platform re-indexes only those. A document deleted locally is not deleted on the platform:
delete it in *Files* (its name is in the previous export, not in the new one; `obsolete-files.ps1` lists these
names). The full update on a PC is described in [deploy/updater/README.md](../updater/README.md).

## Differences with the local version

| Local (Claude CLI) | Production |
|---|---|
| `list_projects`, `find_projects`: exact counts and lists over the whole corpus | search only: non-exhaustive lists (the prompt makes the agent say so) |
| `get_project`: full text of a project | only the most relevant passages |
| impact: Opus, 10 searches (CLI WebSearch), `fetch_page`, score by a second call | gpt-5.1 (EC GPT), 4 SearchApi web searches, score in the report |

These tools can come back as custom components if the need is confirmed in production.
